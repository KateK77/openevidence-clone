## Why CareFlow cost about $3.38

The [reference CareFlow report](https://github.com/KateK77/careflow-ehr/blob/docs/public-showcase-cua100/docs/testing/cua100-v1/results.md) records 336 responses, 586 actions, 1,279,839 input tokens and 12,025 output tokens: $3.3799725 at the same rates. Its 70 read/access probes and 30 writes were mostly shorter, with prepared authentication and known target routes. Its historical level distribution also differs.

MedEvidence includes live retrieval, bilingual synthesis, source-to-claim checks, revisions, account switching, injected failures and multi-format exports. The central estimate has about 3.05× as many responses and 12.2× the output tokens. This is a scenario comparison, not proof that MedEvidence will consume exactly that amount. Reusing CareFlow's dollar total without these workload differences would under-budget this suite.

## Optimizations and remaining fees

The runner uses `gpt-5.4`, reasoning `none`, default service tier, `store:false`, no SDK retries, a 512-token output ceiling and native multi-action batches. It retains the complete task and all action/observation text while sending only the latest native call/screenshot pair. Old screenshots stay in the evidence archive. `previous_response_id` alone is not treated as free historical context.

Desktop screenshots are 1280×800 CSS pixels at device scale 1; mobile tasks use 390×844. Under the documented GPT-5.4 patch calculation these are about 1,200 and 422 image tokens respectively. Screenshot tokens are already in the input totals, not an additional image-generation charge. Identical screenshots share a stored file; necessary observations are never suppressed. See [image token rules](https://developers.openai.com/api/docs/guides/images-vision).

The [pricing tool table](https://developers.openai.com/api/docs/pricing) lists no separate per-call native computer charge for this locally driven setup. Estimate additional tool fees at $0, subject to verification before approval. No hosted browser, hosted container, web-search tool or paid grader is used. The run uses the standard API endpoint, not a regional surcharge endpoint. Token-count requests are tracked separately; no such request is made during this offline phase.

Application synthesis is separate: require a verified free/local model, otherwise BLOCKED. No paid application-model calls are allowed by this configuration. Live PubMed retrieval is outside the OpenAI token bill. This estimate does not authorize buying hosting or other services.

## Coverage with the cap

The fixed execution order has five blocks of 20, each containing 2/4/6/5/3 tasks across Levels 1–5. It does not cherry-pick the easiest tasks. Assuming every prerequisite is ready, the central model predicts approximately **27 tasks at $3, 35 at $4, and 39 at $5**. Actual completed counts may be lower because each request reserves maximum output plus a 10% margin, keeps a $0.01 cushion, and may stop mid-task. These are task-completion budget projections, not predicted pass counts. Current fixture blockers further limit what can be scheduled.

A project-wide persistent ledger prevents budget reset by starting another run. An uncertain charge retains its reservation and stops further calls. Never retry a paid timeout automatically. Reconcile observed usage and any invoice discrepancy before continuation. The $5 cap stops an incomplete run; it cannot make all 100 tasks affordable. **Explicit approval is required before any paid partial run, and full execution remains blocked by the estimate and missing prerequisites.**
